# Notification Intents

> **Status:** Stable
>
> **Last Updated:** 2026-09-12

A **notification intent** is a named business purpose that can produce a notification. It is the
unit of meaning in this subsystem: every notification is generated by exactly one intent, and a
notification that cannot name its intent should not exist.

Intent is also the **extensibility boundary**. New notification behavior arrives as a new intent
with its own rules — not as a new branch inside a shared service. See
[`architecture/notifications/intents/`](../../../../architecture/notifications/intents/README.md).

## Phase 1 intents

| Intent | Kind | Trigger | Selects |
| --- | --- | --- | --- |
| [`TOP_RELEVANT_COMPETITION`](top-relevant-competition.md) | Discovery | Daily scheduled evaluation | Exactly 1 competition |
| [`REGISTRATION_CLOSING`](registration-closing.md) | Deadline | Scheduled deadline evaluation | Top 3 to 5, aggregated into one summary |

Only these two exist. Everything else discussed during design is in
[`future/notification-intents.md`](../future/notification-intents.md) and is not implemented
([ND-I-01](../decisions/intents.md#nd-i-01--phase-1-implements-exactly-two-intents)).

## What every intent must define

An intent is not just a message template. Each one specifies all of the following, and the two
Phase 1 intents answer every row differently — which is why they are separate intents rather than
parameters of one.

| Element | Question |
| --- | --- |
| **Purpose** | What is this notification for, in the user's terms? |
| **Kind** | Discovery, deadline, lifecycle, update, administrative? |
| **Trigger** | What causes an evaluation to run? |
| **User eligibility** | Which users may receive it at all? |
| **Candidate rule** | Which competitions may be considered? |
| **Exclusions** | What removes a candidate before scoring? |
| **Selection policy** | How many ranked candidates are taken? |
| **Aggregation** | One notification per item, or one summary? |
| **Deduplication scope** | What suppresses a future notification of this intent? |
| **User preference** | What can the user configure? |

Compare the two Phase 1 intents on these rows and the design intent becomes visible:

| Element | `TOP_RELEVANT_COMPETITION` | `REGISTRATION_CLOSING` |
| --- | --- | --- |
| Kind | Discovery | Deadline |
| Trigger | Daily at midnight | Approaching deadline evaluation |
| Candidate rule | Registration currently open | Deadline approaching |
| Eligibility relationship | Relevant | Relevant **or** bookmarked |
| Exclusions | Already delivered for this intent | Marked as Registered |
| Selection | Exactly 1 | Top 3 to 5 |
| Aggregation | None — one competition | One summary notification |
| Preference | On / Off | On / Off plus a maximum |

## Rules that apply to every intent

These hold regardless of which intent is being evaluated.

**Intents are independent.** A notification for one intent never suppresses a notification for
another, including for the same competition on the same day
([ND-H-07](../decisions/history.md#nd-h-07--different-intents-are-independent)).

**Deduplication is keyed on intent.** Notification identity is
`(user, competition, intent)`, never `(user, competition)`
([ND-H-06](../decisions/history.md#nd-h-06--deduplication-is-keyed-on-user--competition--intent)).

**A run is not a reason.** An evaluation running produces a notification only if the rules are
satisfied. Silence is a normal outcome
([ND-I-05](../decisions/intents.md#nd-i-05--a-scheduled-run-is-not-a-reason-to-notify)).

**Triggers are not logic.** The evaluation logic must be runnable from a scheduled job, an admin
action, or a future domain event without duplication
([ND-I-04](../decisions/intents.md#nd-i-04--daily-midnight-evaluation-with-the-trigger-separated-from-the-logic)).

**Recipients are limited to what Kizunia knows.** Relevant, bookmarked, and marked-as-registered.
No external participant data
([ND-I-16](../decisions/intents.md#nd-i-16--recipient-rules-use-only-relationships-kizunia-knows)).

**Preferences gate participation.** An intent does not evaluate for a user who has turned it off
([`preferences/notification-preferences.md`](../preferences/notification-preferences.md)).

## Adding an intent later

Adding a new intent should mean **adding new behavior**, not modifying a growing central service
full of conditionals. The implementation contract and the checklist for adding one are in
[`architecture/notifications/intents/adding-an-intent.md`](../../../../architecture/notifications/intents/adding-an-intent.md).

The product-side requirement is simply this: a new intent must answer every row of the table above
before it is built, and the answers belong in a new file in this directory alongside a ruling in
[`decisions/intents.md`](../decisions/intents.md).
